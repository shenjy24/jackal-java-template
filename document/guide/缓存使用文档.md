# Caffeine 本地缓存使用文档

## 设计与边界

项目使用 Caffeine 作为 JVM 本地缓存，并通过 Spring Cache 注解接入。缓存数据不持久化，应用重启即丢失；每个服务实例各自维护缓存，因此多实例部署时允许在 TTL 内出现短暂的数据不一致。需要跨实例共享或严格一致性时，不应使用本地缓存。

缓存适用于读取频繁、写入较少、允许短暂过期且结果集有限的场景，例如用户详情、字典、配置和稳定的权限元数据。不要缓存强一致数据、频繁变化的库存/余额、无限增长的查询结果、敏感数据，或需要跨实例同步的数据。

## 新增缓存

1. 在 `com.tech.common.constant.Caches` 中声明缓存名，并在 `SPECS` 注册最大条目数和写后过期时间。缓存名必须由该类统一管理，不要在业务代码直接写字符串。
2. 在 Query Service 的公开查询方法增加 `@Cacheable`，显式指定 `cacheNames` 与稳定、简单的 `key`；对于可空参数添加 `condition`，对于空结果添加 `unless = "#result == null"`。
3. 在修改或删除该数据的 Command Service 方法上增加 `@CacheEvict(cacheNames = ..., key = ...)`。仅在确实需要整体刷新时使用 `allEntries = true`。

```java
@Cacheable(cacheNames = Caches.CACHE_USER, key = "#userId",
        condition = "#userId != null", unless = "#result == null")
public UserEntity getUser(Long userId) {
    return userDao.getById(userId);
}

@CacheEvict(cacheNames = Caches.CACHE_USER, key = "#userId")
public void updateUser(Long userId, String nickname) {
    // 数据更新成功后自动驱逐该用户缓存
}
```

注解必须放在 Spring Bean 的公开方法上；同一个类中的内部调用不会经过 Spring 代理，也不会触发缓存。Controller、DAO 和 Mapper 不应直接使用缓存注解。

## 策略与维护

`CacheSpec` 的 `maximumSize` 用于限制内存占用，`expireAfterWrite` 用于限制陈旧数据保留时间。先以较短 TTL 和保守容量上线，再依据命中率、数据库压力和堆内存调整。`defaultSpec()` 是新增普通缓存时可复用的默认策略；每个实际缓存仍需显式注册。

注解无法表达的动态 key 或批量操作，可在 Service 中注入 `CacheService` 并调用 `evictCache` 或 `clearCache`。只接受 `Caches` 中已注册的名称，错误名称会立即报错。不要向 HTTP 接口暴露任意清缓存能力。

排查时先检查缓存名和 key 是否与失效操作完全一致，再确认调用是否经过 Spring 代理，以及是否因 TTL、容量淘汰、应用重启或多实例而未命中。
